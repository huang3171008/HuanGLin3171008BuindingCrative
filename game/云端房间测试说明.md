# 云端房间服务：开发测试说明

这是独立副本中的测试实现，**尚未部署到中国大陆公网，尚未通过真实跨平台网络测试，也不是正式运营成品**。现有 P2P 和旧服务器模式保留；云端模式使用独立身份和钱包，首次 5000 金币，不能自动导入或信任原本机钱包。务必保留旧应用和数据。

## 本机测试

需要 Node.js 24 和项目锁定的 `ws` 依赖。进入 `game` 执行：

```sh
npm ci --ignore-scripts
node test-cloud.mjs
node cloud-server.mjs
```

服务默认仅监听 `127.0.0.1:3100`，只用于本机开发。健康检查为 `GET /healthz`；WebSocket 路径 `/ws`。客户端的“服务器房间”输入 `http://127.0.0.1:3100` 仅能在服务器同一台机器的浏览器测试，不代表手机能访问电脑。客户端日常公网配置只接受 HTTPS 域名，连接自动转换为 WSS。

`android/test-cloud-ui.mjs` 在本机启动两个 Chrome 和临时服务，验证界面、房间码和结算。`android/test-peer.mjs` 测试原先的 P2P 流程。均不是两台物理设备或中国大陆公网测试。

## 计划部署（尚未执行）

先由使用者取得和配置云主机、域名、DNS、有效 TLS 证书，并向服务商/主管部门核实适用的备案与权限。服务保持仅监听本地，在同机以 `deploy/Caddyfile.example` 为模板配置 443 HTTPS/WSS 反向代理；不要将示例域名当作真实地址。

安装依赖应在构建或部署副本中运行 `npm ci --omit=dev --ignore-scripts`；审查锁文件和依赖来源。使用 systemd 示例前，实际创建最小权限用户、代码目录和数据目录，确认 Node 可执行文件、日志、访问权限和自启动策略；配置自动证书续签、备份、还原演练、监控及云防火墙。`GAME_TRUST_LOCAL_PROXY=1` **只在反向代理位于同机、后端仅允许本机访问且代理覆盖 `X-Real-IP` 时使用**；其他情况不要启用，避免伪造地址绕过限流。服务端限流和数据结构仍需生产安全审计、负载测试与实际环境调优。

SQLite 单文件以 WAL 模式保存权威房间、钱包和已处理请求；操作及结算使用事务。服务重启后保留已提交数据但所有连接会断开；重启与数据库备份必须考虑 WAL。服务日志只包含事件、随机房间内部 ID、回合和阶段，不记录房间码、令牌、IP、手势或竞猜内容。不要公开 SQLite、凭证或 Android 签名文件。

金币流水在结算事务中写入服务端，客户端可以查看最近 100 条；较早记录仍留在数据库，目前尚无导出和清理界面。每个服务器的长期设备身份凭证保存在设备本地，短期断线优先使用 15 分钟恢复凭证；应用重启后使用本地身份凭证重新认证。清除本地数据会丢失身份，不能以房间码找回。**不要把本地浏览器/应用数据或设备凭证分享给他人。**

当前世界状态仍保存在 SQLite 单行 JSON，逐次操作会读取和重写全局状态，并非可扩展的生产数据库结构。已限制同时连接和匿名玩家数，但不能阻止用户通过创建多个身份重复领取初始金币。发布前需要拆分玩家、房间、回合等表，增加针对恶意客户端的防刷和容量压测，并完成独立安全审计。

暂不支持 WSS 被拦截时的 HTTPS 长轮询回退、集群/跨实例存储和 iOS 已签名发布包；采用单进程，服务端不可用时无法创建或加入房间。网络切换/后台存活、不同 WebView 与校园网策略需真机实测。
